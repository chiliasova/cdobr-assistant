# Помощник по Инструкции ДОУ (кейс ЦДОБР)

Прототип чат-бота для сотрудника. Он отвечает по Инструкции о документообороте со ссылками на конкретные пункты
и честно говорит, когда ответа нет. Ещё он готовит и проверяет проекты приказов и распоряжений по модульным
документам и строит маршрут визирования по Матрице.

Всё работает локально на одном компьютере: open source модель через [Ollama](https://ollama.com), без внешних API
и облака, работает и без интернета.

Полное описание решения: [Помощник ДОУ: архитектура, сценарии и демо](https://claude.ai/artifact/Mt2kTQ6Ty39oGRwPh34afS).

## Быстрый старт (Windows)

1. Установите Ollama и модели (один раз):
   ```
   ollama pull qwen3:4b-instruct-2507-q4_K_M
   ollama pull bge-m3
   ```
2. Установите Python 3.13 (стабильный, не бета) с https://www.python.org/downloads/ (галочка «Add python.exe to PATH»).
3. Скачайте проект и запустите `run.bat` двойным щелчком.
4. Откройте http://127.0.0.1:8000. Демо-входы: `employee / employee` (сотрудник), `doc / doc` (Департамент ДОУ:
   журнал и переиндексация).

Виджет на странице портала: http://127.0.0.1:8000/static/portal-demo.html (кнопка «?» справа внизу).

Демо-проект с ошибками для проверки: `python -m tools.make_bad_draft [путь.docx]` собирает приказ о вводе ИС
с шестью ошибками (см. «Проверка готового проекта»).

## Архитектура и стек

Одно приложение на FastAPI отдаёт веб-интерфейс и API, держит индекс базы знаний и обращается к локальной Ollama
за двумя моделями: языковой и моделью эмбеддингов. Модель только пересказывает найденное и раскладывает описание
по полям модуля. Сроки, визы, сборка и проверка .docx делаются правилами в коде.

```
Браузер (static/: чат, маршрут, проверка, журнал; widget.js для портала)
   │  HTTP, SSE-поток ответа, cookie-сессия
FastAPI (app/main.py) ── SQLite: журнал вопросов и оценок
   ├─ answer.py   подготовка вопроса, правила, проверка ответа
   ├─ search.py   гибридный поиск BM25 + bge-m3, RRF
   ├─ ingest.py   разбор источников data/sources/ на пункты, версия = хеш файлов
   ├─ modules.py  поля модулей, заполнение, чистка, проверка проекта
   └─ routing.py  маршрут по Матрице визирования
         │
Ollama (локально): qwen3:4b-instruct-2507 Q4_K_M, bge-m3
```

| Слой | Технология | Лицензия | Где в коде |
|---|---|---|---|
| Языковая модель | qwen3:4b-instruct-2507 (Q4_K_M) через Ollama | Apache 2.0 | `app/llm.py` |
| Эмбеддинги | bge-m3 через Ollama | MIT | `app/search.py` |
| Поиск по словам | BM25 по леммам, pymorphy3 | MIT | `app/search.py` |
| Сервер и API | Python, FastAPI, uvicorn | MIT / BSD | `app/main.py` |
| Хранилище | SQLite (журнал), файлы индекса | public domain | `app/main.py` |
| Документы Word | python-docx | MIT | `app/modules.py` |
| Интерфейс | статичные HTML, CSS, JS без сборки; поп-ап виджет | наш код | `static/` |

Железо демо: ноутбук Intel i5, 16 ГБ RAM, без видеокарты. Ответ с пересказом занимает 30–60 секунд на CPU.
Сценарии без модели (сроки согласования, реестр замечаний, маршрут, проверка проекта, отказ) отвечают мгновенно.
При запуске модель прогревается и держится в памяти 60 минут.

## Инструкция и база знаний

Источники лежат файлами в `data/sources/`. При запуске программа режет их на фрагменты, и каждый помнит свой номер.
Поэтому бот ссылается на точный пункт, а по клику на ссылку показывает его целиком.

| Источник | Как разбирается | Для чего |
|---|---|---|
| Инструкция по ДОУ (`instruction.txt`) | по пунктам («6.7», «10.3»), 271 фрагмент, приложения отдельно | ответы со ссылками, сроки главы 10 |
| Матрица обязательного визирования (`matrix.md`) | по строкам: вид документа, обязательные визы, условия | маршрут визирования |
| Методические рекомендации по модульным документам (`methodology.md`) | по пунктам | порядок подготовки, чистка по п. 3.3 |
| 7 модулей (`modules/*.docx`) | карточка модуля, поля из сносок и «Примечаний по заполнению» | поиск шаблона, заполнение, проверка |

**Версионность.** Версия базы равна хешу файлов-источников (`ingest.load_all`). Изменился файл, изменилась версия,
и индекс пересобирается.

**Обновление.** Сотрудник Департамента ДОУ заменяет или добавляет файл и нажимает «Переиндексировать»
(кнопка есть только у этой роли). Правила маршрута читаются из самой Матрицы. Новый модуль, оформленный
по тем же правилам (поля со сносками, примечания по заполнению), заполняется и проверяется без программирования.
Чтобы бот сам предлагал для него маршрут, нужна одна строка в `modules.MATRIX_ROW` (модуль → строка Матрицы).

**Другие процессы.** Другая инструкция с нумерацией пунктов разбирается тем же парсером: это одна строка в списке
источников в `ingest.load_all`.

## Поиск и формирование ответа

Ответ строится из найденных пунктов. На каждом шаге есть точка, где бот честно отказывает или показывает пункт дословно.

1. **Подготовка вопроса.** Приветствия и «что ты умеешь» получают короткий ответ без поиска. Явное уточнение
   («а для положения?») склеивается с предыдущим вопросом, новый вопрос не склеивается.
2. **Гибридный поиск.** BM25 по леммам и смысловой поиск по векторам bge-m3, списки объединяются методом RRF.
   Берутся 5 лучших фрагментов с процентом релевантности. Без Ollama работает только BM25.
3. **Порог отказа.** Если лучший фрагмент ниже `MIN_RELEVANCE` (0,35), бот говорит, что в Инструкции ответа нет,
   и направляет в Департамент ДОУ. Модель не вызывается.
4. **Правила вместо модели.** Шаги и сроки согласования (глава 10, п. 10.3), реестр замечаний (п. 10.4–10.5 и
   таблица Прил. № 1) и визы по Матрице выдаются программой напрямую из документов.
5. **Пересказ.** Модель получает вопрос и фрагменты с правилами: отвечать только по ним, ставить ссылки [п. X.Y],
   не переносить правило одного вида документа на другой, а если ответа нет, писать «НЕТ ОТВЕТА». Ответ идёт потоком.
6. **Проверка** (`answer.verify`). Каждая ссылка должна вести на найденный пункт, каждое число должно быть в его
   тексте, каждое предложение должно опираться на источник, условие не должно потеряться (п. 6.7: «от органов
   государственной власти»). Прошло: метка «сверено с источником». Не прошло: пункт дословно.
7. **Подсказки.** Если вопрос про приказ или распоряжение, бот называет модуль, визы по строке Матрицы и предлагает
   скачать шаблон или подготовить проект вместе.

Под каждым ответом ссылки на пункты и кнопки оценки. Оценки попадают в журнал Департамента ДОУ.

## Работа с модулями

**Подготовка проекта.** Бот находит модуль по описанию задачи. Поля читаются из самого .docx: прочерк или вариант
«а / б», сноска [N] даёт подпись и пояснение из «Примечаний по заполнению». Сотрудник пишет описание своими словами,
модель раскладывает его по полям, бот спрашивает недостающее. Новый вопрос выводит из мастера, есть кнопка «Отменить».
python-docx собирает файл и чистит его по п. 3.3 методички: удаляются сноски, скобки, примечания, гриф «УТВЕРЖДАЮ»
и пометка «МОДУЛЬНЫЙ ДОКУМЕНТ», зоны даты, номера и ЭП остаются. В конце бот показывает маршрут визирования.

**Проверка готового проекта** (`modules.analyze_draft`). Бот узнаёт модуль по постоянным формулировкам
и сравнивает с ним загруженный .docx. На демо-проекте он находит шесть ошибок:

| Ошибка | Основание |
|---|---|
| Не заполнена дата ввода в эксплуатацию | Методические рекомендации, п. 3.3 |
| Не выбран вариант «разработанного / измененного» | Методические рекомендации, п. 3.3 |
| Осталась сноска [7] | Методические рекомендации, п. 3.3 |
| Не удалена пометка «МОДУЛЬНЫЙ ДОКУМЕНТ» | Методические рекомендации, п. 3.3 |
| Удалена служебная зона даты и регистрационного номера | Методические рекомендации, п. 3.3 |
| Изменена постоянная формулировка («обеспечить применение») | Методические рекомендации, п. 1.3: полное согласование по главе 10 |

## Пользовательские сценарии

| Сценарий | Сотрудник пишет | Что делает помощник |
|---|---|---|
| Проект по модулю | «Мне нужно подготовить приказ о вводе ИС в эксплуатацию. Что нужно сделать?» | шаги со ссылками, модуль, визы по строке 3 Матрицы, заполнение полей, .docx |
| Сопроводительное письмо | «Можно ли направить служебную записку без сопроводительного письма? …» | «можно» по п. 3.2; как составить письмо, в Инструкции не регламентировано |
| Проверка проекта | «Я подготовил приказ на основе модуля. Проверь его…» | загрузка .docx, замечания со ссылками, «Что дальше», маршрут |
| Согласование | «Как организовать согласование большого нормативного документа…», затем «а для положения?» | шаги по главе 10, сроки из п. 10.3, затем 10 рабочих дней для положения |
| Реестр замечаний | «Как оформить реестр замечаний от нескольких подразделений?» | п. 10.4–10.5 и таблица Прил. № 1 для скачивания |
| Точный срок | «Что делать с документом с отметкой «Срочно»?» | 3 рабочих дня для документов органов власти [п. 6.7], условие сохраняется |
| Честный отказ | «Какая погода в Ростове?» | «в Инструкции ответа нет», без вызова модели |
| Маршрут | вкладка «Маршрут» | вид документа, уточняющие условия, пронумерованные визы |
| Журнал | вкладка «Журнал» (роль Департамента ДОУ) | вопросы и оценки, переиндексация |

## Безопасность

- Модель и эмбеддинги в локальной Ollama, данные не покидают компьютер.
- Вход по логину и паролю, сессия подписана HMAC (`CDOBR_SECRET`). В банке: корпоративная учётная запись и HTTPS.
- Роли «сотрудник» и «Департамент ДОУ» (журнал, переиндексация). В банке: роли из групп корпоративного каталога.

## Настройки (переменные окружения)

`OLLAMA_URL` (по умолчанию `http://127.0.0.1:11434`), `LLM_MODEL`, `EMBED_MODEL`, `USE_LLM=0` (только цитаты),
`USE_EMBEDDINGS=0` (только BM25), `MIN_RELEVANCE`, `TOP_K`, `CDOBR_SECRET`.

## Тесты

```
.venv\Scripts\python -m pytest -q
```
Тесты используют заглушку Ollama (`tests/fake_ollama.py`) и не требуют моделей.

Документы в `data/sources/` — учебные материалы кейса, выданные организаторами хакатона.
